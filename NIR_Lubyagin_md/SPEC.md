# Спецификация проекта: ИТ-конвейер причинно-следственного анализа и Uplift-моделирования для e-commerce

> Источник требований: отчёт о НИР «Исследование и моделирование причинно-следственных связей в больших транзакционных данных электронной коммерции для оптимизации принятия решений» (`NIR_Lubyagin.md`, МАИ, Институт №8, 2026).
>
> **Исходное состояние: пустой репозиторий.** Документ описывает систему, которую требуется построить целиком — от загрузки сырых логов до демонстрационного дашборда. Все положения НИР трактуются как требования к реализации, а не как описание готового кода.

---

## 1. Контекст и постановка

### 1.1 Решаемая проблема

Классические предикативные модели (supervised ML на градиентном бустинге / нейросетях) оптимизируют вероятность отклика `P(Y=1|X)`, а не инкрементальный эффект воздействия. Как следствие промо-бюджет уходит на «органических покупателей» (*Sure Things*), которые совершили бы покупку и без скидки, — происходит каннибализация маржи.

Требуется система, которая вычисляет **индивидуальный условный эффект воздействия (CATE / Uplift)**:

```
τ(x) = E[Y | do(T=1), X=x] − E[Y | do(T=0), X=x]
```

вместо смещённой наблюдаемой разности `Δ_corr = E[Y|T=1] − E[Y|T=0]` (формула 1 отчёта), и направляет купоны только в сегмент *Persuadables*.

### 1.2 Цель

Разработать и программно реализовать масштабируемый модульный ИТ-конвейер причинно-следственного анализа больших транзакционных данных, обеспечивающий полный цикл: сырые логи → матрица признаков → графовая идентификация эффекта → расчёт Uplift-скоров → аудит причинности → сегментация и BI-визуализация.

### 1.3 Гипотеза, подлежащая проверке

Учёт направленных графовых ограничений (DAG + backdoor) и двухэтапное мета-обучение **X-Learner на базе LightGBM** повышают устойчивость Uplift-прогноза к сильному дисбалансу классов (группа воздействия < 15% выборки) по сравнению с классическими предикативными классификаторами.

**Операционализация гипотезы (критерий подтверждения):** на отложенной выборке AUUC и Qini-коэффициент X-Learner+LightGBM статистически значимо превосходят baseline-модели (см. §7.3) при bootstrap-доверительных интервалах 95%.

### 1.4 Границы (scope)

| В scope | Вне scope |
|---|---|
| Батчевый расчёт Uplift-скоров по историческим логам | Онлайн-инференс / real-time scoring API |
| Локальный/одноузловой запуск на Python 3.13 | Реальный Spark/распределённый кластер (архитектура должна допускать перенос, но не реализуется) |
| Демонстрационный Streamlit-дашборд | Промышленный BI с ролевой моделью и SSO |
| Датасет RetailHero (X5 Retail Group) | Интеграция с живыми продуктовыми БД |
| Refutation-тесты DoWhy | Запуск реальных A/B-тестов |

## 5. Слой 1 — Данные и ETL (W2–W4)

### 5.1 Источник

Датасет **RetailHero Uplift Modeling (X5 Retail Group)**, публичные файлы:

| Файл | Ключевые поля |
|---|---|
| `clients.csv` | `client_id`, `first_issue_date`, `first_redeem_date`, `age`, `gender` |
| `uplift_train.csv` | `client_id`, `treatment_flg` (T), `target` (Y) |
| `purchases.csv` | `client_id`, `transaction_id`, `transaction_datetime`, `purchase_sum`, `store_id`, `product_id`, `product_quantity`, `regular_points_received/spent`, `express_points_received/spent`, `trn_sum_from_iss`, `trn_sum_from_red` |
| `products.csv` | `product_id`, `level_1..level_4`, `segment_id`, `brand_id`, `vendor_id`, `netto`, `is_own_trademark`, `is_alcohol` |

> ⚠ **Условие дисбаланса, требующее решения на этапе EDA (W3).** В НИР заявлено соотношение T=1 : T=0 = 15% : 85%. В публичном `uplift_train.csv` соотношение близко к паритету (~50/50) — это необходимо проверить фактическими данными в EDA и зафиксировать в `reports/eda_summary.md`. Режим дисбаланса задаётся явно параметром `data.treatment_share` и реализуется стратифицированным даунсэмплингом treatment-группы (сид фиксирован). Пайплайн логирует фактическую долю в каждом прогоне; эксперимент проводится **минимум в двух режимах** — native и `treatment_share=0.15` — чтобы проверить гипотезу §1.3 именно на дефицитной целевой выборке.

### 5.2 Требования к ETL

- **ETL-1.** Загрузка из CSV/Parquet с явной схемой типов; невалидные строки — в карантинный файл, не в тихий drop.
- **ETL-2.** Дедупликация по `(client_id, transaction_id, product_id)`.
- **ETL-3.** Отсечение транзакций вне окна наблюдения; окно задаётся в конфиге (`observation_window_days`, `outcome_window_days = 7`).
- **ETL-4.** Нормализация числовых признаков по Z-score; параметры (`mean`, `std`) считаются **только на train** и сохраняются в `artifacts/scaler.json` (защита от утечки).
- **ETL-5.** Кодирование категориальных: `gender` — one-hot, высококардинальные (`store_id`, `brand_id`) — частотное/целевое кодирование, посчитанное на train-фолде.
- **ETL-6.** Выход — `data/processed/feature_store.parquet` со строгим контрактом: `client_id`, ≥30 колонок `X`, `treatment` (int8), `target` (int8), `revenue` (float, опционально).
- **ETL-7.** Чанковая обработка `purchases` (итератор по партициям) — конвейер не должен требовать загрузки всех транзакций в RAM целиком.

### 5.3 Витрина признаков (≥ 30 ковариат)

| Группа | Примеры |
|---|---|
| Recency | дни с последней покупки, дни с `first_issue_date`, дни с `first_redeem_date` |
| Frequency | число транзакций за 7/30/90 дней, число активных дней, частота сессий за 30 дней |
| Monetary | средний чек, медианный чек, суммарный объём покупок, std чека, max чек |
| Лояльность | начислено/списано regular- и express-баллов, доля покупок с использованием баллов (`trn_sum_from_red / purchase_sum`) |
| Ассортимент | число уникальных категорий `level_1..level_4`, доля СТМ, доля алкоголя, число уникальных store_id |
| Соц-дем | `age`, `gender`, возрастные бины |
| Тренды | отношение активности 30д / 90д (признак затухания), слоуп суммы покупок |

**Контроль мультиколлинеарности:** строится треугольная матрица парных корреляций Пирсона/Спирмена; при `|r| > 0.95` один из признаков помечается на исключение (отчёт `reports/corr_matrix.png` + список удалённых в `reports/dropped_features.json`).

## 6. Слой 2 — Причинно-следственный модуль (W5, W9)

### 6.1 Граф

Базовый DAG (рис. 1 отчёта): ковариаты `X` — общая причина воздействия и исхода.

```
X ──▶ T
X ──▶ Y
T ──▶ Y
```

Граф хранится декларативно (`configs/dag.gml`), а не хардкодится в коде, — расширяемая версия должна допускать разбиение `X` на подгруппы (соц-дем, поведение, лояльность) и добавление сезонности как отдельного узла.

### 6.2 Интерфейс

```python
# src/causal_uplift/causal/identify.py
def build_model(df, treatment: str, outcome: str, graph_path: str) -> dowhy.CausalModel: ...
def identify(model) -> IdentifiedEstimand: ...          # метод backdoor
def estimate_ate(model, estimand, method: str) -> EstimateResult: ...
```

### 6.3 Требования

- **CAU-1.** `identify_effect()` обязан вернуть backdoor-estimand; если эффект неидентифицируем — конвейер останавливается с явной ошибкой, а не переходит к Слою 3 (gate из §1.3 отчёта).
- **CAU-2.** Вычисляются и логируются обе величины: наблюдаемая разность `Δ_corr` (формула 1) и скорректированный `ATE` (формула 2). Их расхождение — количественная иллюстрация величины смещения конфаундеров, обязательный артефакт для ВКР.
- **CAU-3.** Оценка ATE минимум двумя методами (`backdoor.propensity_score_weighting` и `backdoor.linear_regression`) для перекрёстной проверки.
- **CAU-4.** Выход: `artifacts/estimand.json` + `reports/ate_summary.md`.

### 6.4 Аудит причинности (Refuters, W9)

| Тест | Ожидаемое поведение робастной модели |
|---|---|
| `random_common_cause` | Оценка эффекта меняется незначимо (p-value > 0.05) |
| `placebo_treatment_refuter` | Новый эффект ≈ 0, статистически неотличим от нуля |
| `data_subset_refuter` | Оценка стабильна при удалении случайных 10–20% данных |
| `add_unobserved_common_cause` (доп.) | Строится кривая чувствительности к силе ненаблюдаемого конфаундера |

Каждый тест прогоняется с фиксированным сидом, результат — строка в `reports/refutation.md` с вердиктом PASS/FAIL по порогам из конфига.

## 7. Слой 3 — Вычислительное ядро (W6, W7)

### 7.1 Алгоритм X-Learner

Три шага (§1.3 отчёта), реализуются через `econml.metalearners.XLearner` с базовыми моделями LightGBM:

1. **Outcome-модели.** Обучаются `μ₁ = LGBM(X | T=1)` и `μ₀ = LGBM(X | T=0)`.
2. **Импутация контрфактических эффектов.**
   `D₁ᵢ = Yᵢ − μ₀(Xᵢ)` для treatment-группы; `D₀ᵢ = μ₁(Xᵢ) − Yᵢ` для control-группы.
   Затем обучаются `τ₁ = LGBM(D₁ | X)` и `τ₀ = LGBM(D₀ | X)`.
3. **Взвешивание по propensity.**
   `τ(x) = g(x)·τ₀(x) + (1 − g(x))·τ₁(x)`, где `g(x)` — propensity score.

**Ключевое защищаемое положение НИР** (двухуровневая импутация): при дефицитной treatment-группе бóльший вес получает `τ₀`, обученная на избыточной контрольной группе, — это и даёт стабилизацию против переобучения на несбалансированных данных. Реализация обязана явно логировать распределение `g(x)` и фактические веса, чтобы этот эффект был измерим, а не декларативен.

### 7.2 Интерфейс

```python
# src/causal_uplift/models/xlearner.py
class UpliftXLearner:
    def __init__(self, lgbm_params: dict, propensity_params: dict, random_state: int): ...
    def fit(self, X: pd.DataFrame, T: np.ndarray, Y: np.ndarray) -> "UpliftXLearner": ...
    def predict_uplift(self, X: pd.DataFrame) -> np.ndarray:  # CATE τ(x)
        ...
    def save(self, path: str) -> None: ...
    @classmethod
    def load(cls, path: str) -> "UpliftXLearner": ...
```

### 7.3 Baseline-модели для сравнения (обязательны для таблиц W8)

| Baseline | Назначение |
|---|---|
| Random targeting | нижняя граница, нулевая линия Qini |
| LightGBM-классификатор `P(Y=1|X)` | «наивный» подход из §Введение, демонстрация каннибализации |
| Two-Model (T-Learner) | базовый uplift-подход |
| S-Learner | treatment как обычный признак |
| X-Learner + LightGBM | **целевая модель** |

### 7.4 Требования

- **ML-1.** Фиксированный `random_state` во всех компонентах; полная воспроизводимость прогонов.
- **ML-2.** Стратифицированный сплит по паре `(T, Y)`, доли train/valid/test в конфиге; поддержка k-fold cross-fitting для устойчивости оценок.
- **ML-3.** Поддержка sparse-матриц и нативной работы LightGBM с категориальными признаками.
- **ML-4.** Защита от переобучения: `early_stopping` по валидационной выборке для каждого base learner.
- **ML-5.** Логирование всех прогонов (параметры + метрики + артефакты) в локальный трекинг (MLflow либо JSON-журнал `artifacts/runs/`).
- **ML-6.** Бюджет ресурсов: обучение полного пайплайна на RetailHero — не более 30 минут на 8-ядерной машине без GPU.

## 8. Слой 4 — Оценка, сегментация, BI (W8, W10, W11)

### 8.1 Метрики

| Метрика | Требование |
|---|---|
| **AUUC** | площадь под кривой кумулятивного прироста; основная метрика сравнения моделей |
| **Qini coefficient** | нормированная площадь между Qini-кривой и случайным таргетингом |
| **Uplift@k** | k ∈ {10%, 20%, 30%} — инкремент в топ-k по скору |
| **Weighted average uplift** | по децилям |

Кривые Qini и uplift-по-децилям сохраняются в `reports/` в PNG + исходные значения в CSV (для вставки в ВКР).

### 8.2 Сегментация на 4 квадранта

Классификация по знаку `τ(x)` и порогам из конфига:

| Сегмент | Условие | Действие |
|---|---|---|
| **Persuadables** («Убеждаемые») | `τ(x) > θ_high` | **отправить купон** |
| **Sure Things** («Органические») | `τ(x) ≈ 0`, высокая `P(Y=1|T=0)` | не беспокоить — купон съедает маржу |
| **Lost Causes** («Безнадёжные») | `τ(x) ≈ 0`, низкая `P(Y=1|T=0)` | не тратить бюджет |
| **Sleeping Dogs** («Не беспокоить») | `τ(x) < θ_low` (отрицательный) | исключить из коммуникации |

Пороги `θ_high`, `θ_low` задаются в конфиге; по умолчанию — квантильные.

### 8.3 Экономика кампании

Модуль `economics/budget.py` рассчитывает по тестовой выборке:

```
economy = (N_total − N_persuadables) × cost_per_coupon
incremental_revenue = Σ_{i ∈ targeted} τ(xᵢ) × avg_margin
ROI = (incremental_revenue − N_targeted × cost_per_coupon) / (N_targeted × cost_per_coupon)
```

Ориентир из §Введение отчёта — сокращение неэффективных маркетинговых расходов на 15–20%; фактическое значение фиксируется по результатам эксперимента, а не постулируется.

### 8.4 Streamlit-дашборд

Обязательные экраны:

1. **Обзор** — ATE, Δ_corr, размер выборки, доля treatment, вердикты refutation-тестов.
2. **Качество модели** — Qini-кривая и кривая кумулятивного прироста (целевая модель vs baselines), таблица AUUC / Qini / uplift@k.
3. **Сегментация** — распределение `τ(x)`, доли четырёх квадрантов, drill-down по сегменту с топ-признаками.
4. **Калькулятор бюджета** — слайдеры `cost_per_coupon`, `avg_margin`, доля охвата → экономия, инкрементальная выручка, ROI.
5. **Аудит причинности** — результаты Placebo Treatment и Random Common Cause с визуализацией сдвига оценки.

Требования: дашборд читает готовые артефакты из `artifacts/`, не переобучает модель в рантайме; холодный старт < 5 с.

## 11. Качество и тестирование (W12)

| Уровень | Требование |
|---|---|
| Unit | метрики (AUUC/Qini) проверяются на синтетических данных с аналитически известным ответом |

## 12. Критерии приёмки проекта

1. `make all` на чистой машине воспроизводит полный цикл: окружение → данные → ETL → признаки → DAG → обучение → метрики → refutation → артефакты для дашборда.
2. Проведён EDA, в `reports/eda_summary.md` зафиксировано фактическое соотношение `T=1 / T=0`, профиль пропусков и распределение целевой метрики.
3. Витрина содержит **≥ 30 ковариат**, нормированных Z-score, с отчётом по мультиколлинеарности.
4. DoWhy возвращает backdoor-estimand; зафиксированы и `Δ_corr`, и скорректированный `ATE` с комментарием о величине смещения.
5. Реализован X-Learner + LightGBM; получены AUUC и Qini **в двух режимах** — native и `treatment_share=0.15`.
6. Сводная таблица сравнения с ≥ 4 baseline-моделями; превосходство целевой модели подтверждено bootstrap CI 95% либо явно зафиксировано как неподтверждённое (отрицательный результат допустим и должен быть описан).
7. Все три refutation-теста отработали, вердикты занесены в `reports/refutation.md`.
8. Streamlit-дашборд запускается командой `make app` и содержит все пять экранов §8.4.
9. Подготовлены `docs/architecture.md`, `docs/hyperparameters.md` и выгрузка графиков/таблиц для ВКР.
10. Тесты §11 зелёные, воспроизводимость по сиду подтверждена двумя независимыми прогонами.

## 14. Риски и смягчение

| Риск | Проявление | Смягчение |
|---|---|---|
| Несовместимость версий `dowhy`/`econml`/`numpy` под Python 3.13 | Невозможность собрать среду, блокировка всего проекта | Проверка сборки первым шагом Э0; при конфликте — откат на Python 3.12 с фиксацией отступления в документации |
| Расхождение заявленного дисбаланса 15/85 с фактическим датасетом | Условие гипотезы не воспроизводится | Явный параметр `treatment_share`, два режима эксперимента, логирование фактической доли (§5.1) |
| Слабый истинный эффект купона | AUUC ≈ случайный таргетинг, гипотеза не подтверждается | Зафиксировать отрицательный результат честно; sanity-тест на синтетике с известным `τ(x)` отделяет «эффекта нет в данных» от «модель сломана» |
| Утечка целевой переменной через кодирование/скейлинг | Завышенные метрики | Leakage-тест §11, fit только на train |
| Нестабильность propensity score (значения у 0 или 1) | Взрыв весов в X-Learner | Клиппинг propensity в `[0.01, 0.99]`, логирование распределения `g(x)` |
| Переобучение base learners на дефицитной treatment-группе | Шумный `τ₁` | Early stopping, `min_child_samples`, cross-fitting |
| Объём данных не помещается в RAM | Падение ETL | Чанковая обработка Parquet (ETL-7), агрегаты вместо хранения всех транзакций |
| Недоступность публичного датасета RetailHero | Нет входных данных | Зеркалирование архива локально на Э1; резервный вариант — Criteo Uplift Prediction Dataset с переопределением витрины признаков |
